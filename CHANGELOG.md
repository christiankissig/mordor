## [Unreleased]

### Added
- In the web UI, a funnel button beside *Also allowed by* restricts the execution carousel to the executions the primary model allows and no compared model does, and the carousel label counts them (*Execution 3 of 25 · 4 only sMRD*). The row now shows whenever models are compared, saying *none* for an execution only the primary allows, so the button stays in reach. A saved run keeps which models were compared. In the settings dialog, the compared model that is already the primary is greyed out, and under *Default* that is the model the test's first assertion names, or sMRD. The manual describes both, and no longer says IMM cannot be compared.
- Episodicity tests for the Treiber stack and the Michael-Scott queue, `programs/episodicity/treiber-1.lit`, `msqueue-enqueue-1.lit` and `msqueue-dequeue-1.lit`, with C11 orderings and no reclamation. The stack's push and pop loops are episodic. The queue's enqueue and dequeue are not, and only because of the helping CAS that swings a lagging tail: the next iteration reads tail from it (write condition), and in the dequeue nothing orders that release write to tail before the next acquire read of head (events condition). `msqueue_without_helping/` has both loops without it, and they are episodic. Enqueue and dequeue in one program do not finish in 12 minutes, so the queue is checked one operation per file.
- The litmus programs of Arlt and Vafeiadis, *RGSep under Release/Acquire Consistency* (OOPSLA 2026), in `litmus-tests/oopsla26_rgsep/`: IRIW, CohRR, MP with and without the spin loop, MP ‖ MP, Coh and OT, release-acquire throughout, and relaxed variants of CohRR, MP and Coh. Each asserts the paper's RA verdict and herd7's on the C translation in `herd/` under SC, TSO, RA, SRA, WRA, Coherence and RC11, on all 63 of which MoRDor agrees. herd7 and MoRDor part with the paper on Coh: it calls Coh's weak outcome possible under relaxed C11 and SCOH, but RC11 and Coherence forbid it, and only WRA allows it. `MP-repeat.lit`, the paper's spin loop, asserts SC, RA, RC11, PS1 and PS2.
- Eight OCaml litmus tests in `litmus-tests/rmm-zoo/models/ocaml/`, the shapes Dolan, Sivaramakrishnan and Madhavapeddy (PLDI 2018) use to set OCaml apart: races bounded in the past and in the future (Examples 2 and 3), load buffering with a data, a control and a false dependency, read-read coherence over writes of two threads, an atomic write that acquires as well as releases (§9.2), and IRIW over atomics. Each asserts OCaml's verdict and, where they differ from it, RC11's and sMRD's. OCaml and RC11 part on two of them: OCaml allows `CoRR+sync` and RC11 forbids it; RC11 allows `AtomicWrite+acquire` and OCaml forbids it. On load buffering they agree. sMRD allows `RaceInFuture`, `LB+data` and `LB+falsedep+data`, which OCaml forbids.
- Episodicity tests for each case of the write condition (Condition 2), `programs/episodicity/mem_cases/`: for cases (a), (b) and (c), a loop the case admits and one it fails. MoRDor reports `case_b_fails.lit` episodic, its write condition not following `dp ∪ rf` through other threads; the test states what MoRDor does and its comment what the definition says.
- Two more case (b) tests, `programs/episodicity/caseb_no_derived_writes/`, in which another thread relays an iteration's write to a later one by a control or a data dependency, though no write stores a value derived from a read. MoRDor reports both episodic, as for `case_b_fails.lit`. Each loop ends in an SC fence so that Condition 4 holds: since Condition 4 filters `ppo_loc_base`, release and acquire alone no longer order an iteration's write before the next iteration's read. `caseb_path.py` beside them counts the executions of the `executions` export that have the `(dp ∪ rf)+` path.
- **Promising semantics 1.0 and 2.0.** `--semantics ps1` or `--semantics ps2` computes a program's executions under the promising semantics of Kang et al. (POPL 2017) or Lee et al. (PLDI 2020) instead of sMRD's; `--semantics smrd` is the default. The new `Promising` module explores machine states explicitly -- messages with timestamp intervals and views, per-thread views, promises and their certification, PS2.0's reservations and capped memory -- and turns each distinct final outcome into an execution, so the same `Assertion` step checks it. `Semantics.step_calculate_executions` is the pipeline step that chooses between them. Under a promising semantics an `[Promising]` (or `[PS1]`, `[PS2]`) annotation is accepted; under sMRD it stays an error, now pointing at `--semantics`. Only `run` supports the promising semantics; the commands that show justifications, dependencies or futures refuse it. Assertions about relations and refinement chains are refused too, since promising executions are outcomes rather than event graphs.
- A `[PS1]` or `[PS2]` annotation selects promising semantics 1.0 or 2.0, as `[IMM]` selects a coherence model; `--semantics` chooses a version for a whole run and takes precedence. A bare `[Promising]` names no version and is an error unless one is chosen. The tests in `litmus-tests-promising/` are annotated `[PS1]` and are now part of the integration suite; all 20 hold under both versions.
- The web UI's settings dialog offers PS1.0 and PS2.0 as the primary model and as compared models. As the primary model they replace the test's own annotation, like any other, and each execution's graph shows its `rf` and `co`. Promising semantics enumerates executions of its own, so it is compared with the other models by outcome: a model allows an execution when it allows the execution's final values, which for sMRD's symbolic executions the solver decides (`Assertion.admits_outcome`). Symbolic loops are unavailable while a promising model is involved. The JSON executions export stays sMRD's and says so.
- The web UI's settings dialog offers C11, C++17 and C++20 as the primary model and as compared models, and the manual's model table describes them.
- The web UI's settings dialog offers every model MoRDor supports as the primary model and as a compared one, IMM included, which the server also used to drop from a request. RC11c is not offered: its only configuration, `with_consume`, is read by nothing, so it answers as RC11. The manual says so. A request naming a model the server does not offer, as primary or compared, is now an error naming it, where the server used to run the default model or drop the compared one without saying so.
- **ORC11 and RAR** as coherence models, `[ORC11]` and `[RAR]`, configurations of the `RC11` functor defined on fragments of RC11. ORC11 (Dang et al., POPL 2020), the operational model RustBelt verifies Rust's libraries against, is RC11 without SC accesses or SC fences; its paper sketches the correspondence. RAR (Doherty et al., PPoPP 2019) is RC11's release-acquire/relaxed fragment, which its paper proves its operational semantics equivalent to: relaxed, release and acquire accesses and updates, no fences, non-atomic or SC accesses. `RC11Config.fragment` says which programs a model is defined on, and the model refuses a program with an event outside it, naming the event, rather than answer as RC11. `litmus-tests/rmm-zoo/models/rc11-fragments/` has four tests on which herd7 under `rc11.cat` agrees. The web UI and the manual offer both.
- **Wasm** as a coherence model, `[Wasm]`: WebAssembly's memory model (Watt, Rossberg and Pichon-Pharabod, OOPSLA 2019, Fig. 7). Accesses in mode `sc` are seqcst and every other access unordered; synchronisation is `rf` between seqcst accesses, and the sc-last-visible conditions, including the (†) and (‡) the paper adds to JavaScript's model, are decided by searching for a total order of the seqcst accesses. Unordered accesses need not be coherent, so the model reads no coherence order; a race is defined, not undefined; and it allows out-of-thin-air executions. MoRDor's accesses are each to one whole location, so all are aligned and tear-free, and the paper's mixed-size behaviour does not arise. Programs with fences, locks or release/acquire modes are refused. `litmus-tests/rmm-zoo/models/wasm/` has the paper's Fig. 1 (incoherent unordered reads, allowed) and Fig. 10 (the JavaScript SC-DRF violation, forbidden), with SB, MP and thin-air load buffering.
- **DRFx, DeNovoSync, BMM, CRC and OCaml** as coherence models, the zoo models for which a race predicate was thought the only missing primitive. DRFx (Marino et al., PLDI 2010) and DeNovoSync (Sung and Adve, ASPLOS 2015) are SC for data-race-free programs, with a race between accesses one of which is `na` reported as undefined behaviour. BMM (Demange et al., POPL 2013) is TSO where a store and a later load stay in order when either is volatile, written `sc`; it needs no race clause, its external DRF being a theorem rather than an axiom. CRC (Dodds, Batty and Gotsman, ESOP 2018) is C11's release-acquire fragment with catch-fire non-atomics and totally ordered SC fences. OCaml (Dolan, Sivaramakrishnan and Madhavapeddy, PLDI 2018) is the paper's axiomatic model, with `sc` accesses as atomic locations; races are defined and load buffering forbidden, so it has no race clause either. Each refuses programs outside the fragment it is defined on. `AxiomaticWith` is the `Axiomatic` functor with a race clause, `allows_thin_air` and a program check. `litmus-tests/rmm-zoo/models/{drf,bmm,crc,ocaml}/` test them, each `forbid` checked to have a candidate execution the model rejects.
- **JAM** as a coherence model, `[JAM]`: Java Access Modes (Bender and Palsberg, OOPSLA 2019), the herd model of their Appendix A. `na` is Java's plain, `rlx` opaque, `acq`/`rel` release-acquire, `sc` volatile. Its coherence order is its own, partial and derived from visibility, with the trace order the model needs for full fences, volatiles and RMWs searched; the final writes are the candidate order's last. Plain accesses are coherent but may be out of thin air, so JAM allows out-of-thin-air executions. The paper's fence filters are not published and are reconstructed from the JDK's fence specifications. `litmus-tests/rmm-zoo/models/jam/` has 16 tests, on 14 of which herd7 under a transcription of Appendix A, `jam.cat` in the same directory, gives the same verdict, the paper's Fig. 12 IRIW variants among them.
- **An out-of-thin-air execution is admitted only if its elisions are within one thread.** sMRD's write elision drops an initialising store that another thread overwrites, through the fork. In an execution with a cycle in `dp ∪ ppo ∪ rf`, which only a model allowing thin air sees, that left reads of the initial event with a value nothing wrote: JAM allowed load buffering over opaque accesses at 42 through it, though its causality axiom forbids that shape. Executions without the cycle are unaffected. Three goldens under C11 and Wasm lose that one execution each and keep their verdicts.
- **An oracle for the distributed consistency models.** `test/oracles/distributed_models.py` decides Local, Slow, PRAM, Causal, PC, POCausal and the session guarantees from their definitions over histories, independently of MoRDor's executions, and agrees with all 80 verdicts the Steinke–Nutt and session tests assert. `test/oracles/compare_with_mordor.py` compares the two on random programs: every disagreement is an outcome the definitions allow that MoRDor's candidate executions cannot express (a read of its own thread's later store, a read skipping its own latest store, load buffering on one location), and none runs the other way. `litmus-tests/rmm-zoo/models/steinke-nutt/README.md` states and justifies the encoding.
- **C11, C++17 and C++20 allow out-of-thin-air executions.** Candidate generation dropped every execution with a cycle in reads-happen-before, `dp ∪ ppo ∪ rf`, before any model was asked, so the standard's models, which have no thin-air axiom, gave RC11's answers on thin-air tests. `MEMORY_MODEL.allows_thin_air` says which models allow them; when one of a run's models does, the generator keeps those executions, and every model that does not rejects them at admission. One enumeration still serves every model of a run. `litmus-tests/rmm-zoo/models/cpp-thin-air/LB+datas.lit` allows `r1 = r2 = 42` under the three and forbids it under RC11, IMM, sMRD, SC and RA. herd7 is no oracle here: it answers Never under `cpp11.cat` as well, since its candidate generation never makes a value out of a circular dependency.
- Under `--semantics ps1|ps2`, assertions can ask about `.rf`, `.co`, `.rmw` and `.po`. Each access of a promising run is matched to its event in the interpreted event structure -- by source span, program order, and the path condition the values it read satisfy -- so the relations carry the labels sMRD's do. A read of an initial value has no `rf` edge, as under sMRD. Tracking them costs states, so it is only on when an assertion asks. `.dp` and `.ppo` remain sMRD's own.
- Undefined behaviour under promising semantics is reported: a null dereference or division by zero aborts the run, as PS2.0's `abort` does, and `forbid (ub)` fails on it.
- **C11, C++17 and C++20** as coherence models, `[C11]`, `[C17]` and `[C20]` (also `[cpp11]`, `[cpp17]`, `[cpp20]`), configurations of the `RC11` functor. C11 and C++17 take the zoo's `cpp11.cat` and `cpp17.cat` release sequences with C11's own SC, the conditions on its order `S` as herd's `c11_partialSC.cat` states them, so they allow IRIW with SC fences as the standard did before P0668; C++20 has C++17's release sequence with RC11's `psc`. None has a thin-air axiom. They agree with herd7 on twelve SC shapes and on the whole release-sequence family. The 18 tests that sat in `litmus-tests-cpp/` are back in the suite under `litmus-tests/rmm-zoo/`, asserting all three models' verdicts; `models/cpp-release-sequences/README.md` compares them with herd7.
- **Data races are undefined behaviour** under every model with a race clause: `rc11`, `rc11c`, `rc17`, `rc11z`, `od-lso`, `c11`, `c17` and `c20` report conflicting accesses of two threads, one of them non-atomic, that `hb` leaves unordered in a consistent execution, as herd's `undefined_unless empty dr`. A `Race` UB reason carries the pairs, so `allow (ub)` and `forbid (ub)` can ask about them. `MEMORY_MODEL` gains `data_races`; `Coherence.data_races` searches for an admitted coherence order with a race, since under C++11's release sequences the order decides `hb`. Plain `:=` accesses are relaxed, so no existing test changes verdict.
- `--output-mode isa` lists each execution's events under `events`, so a label missing from a future means the event is absent from that execution, not an event no edge touches.
- **Strengthening, where it enables a lift.** sMRD's strengthening may conjoin any predicate to a justification; `StrengthenLiftElab` conjoins the one lifting needs. For two conflicting writes to the same location that differ only in the value written, it adds the equation between the values to both, value-assigns them and lifts the pair, keeping the equation in the lifted predicate. `own/FWD-STRENGTHEN-LIFT.lit` (#90), parked since value assignment stopped discharging unrelated conjuncts, now holds and is back in the suite; `own/paper112F.lit` gains `x := 1` justified under `r1 = 1` without the read of `y`, and `fwd/rlx/lift_F1r.lit` gains four executions. Minimality pruning of freeze results and executions now lets one result evict another only where the evicted one's predicate entails the survivor's: a strengthened execution, valid only under its equation, had pruned the general one and lost `r1 = 0, r2 = 0` from `paper112F` (`own/paper112F-unstrengthened.lit`).
- Seven litmus tests from Ševčík's thesis in `litmus-tests/sevcik_thesis/`: the monitor-protected load and store buffering of Figure 1.1B and Example 2.5, which need lock order and failed before it; the thin-air load buffering of Figure 5.1C and Example 2.7; Example 2.6's volatile flags as release/acquire; Figure 6.1's branch with the same write on both arms; and the roach-motel transformed program of §5.3.3, which the JMM allows and sMRD forbids. Each states the thesis' verdict, and MoRDor agrees with all seven. `litmus-tests-jmm/sevcik_thesis/Redundant Read after Read Elimination.lit` and `Reordering with external actions.lit` record the thesis' JMM verdicts (§5.3.2 and §5.3.5); the second's `print` is a comment, since MoRDor has no external actions.

### Fixed
- **Forwarding substitutes the forwarded value** (#46). sMRD's Forwarding applies `[val(e₂) ↦ val(e₁)]` to the predicate and to the justified write; MoRDor only added the edge, so a forwarded read's symbol stayed in the predicate and kept the dependency forwarding exists to remove. Forwarding into a read now substitutes, and a justification whose predicate becomes `false` is dropped. Load forwarding `r1 := x` onto `r2 := x` discharges `if (r1 = r2)`, so `esop_problem/RRE.lit` (ESOP 2015) is allowed and back in `litmus-tests/`; JCTC2 and JCTC3 are allowed under sMRD too. Forwarding an initialiser does the same: `own/coproductReorder.lit` now allows `r1 = 1`, since `y := 1` is never overwritten and `z := 1` lifts out of the branch, and four volatile-lifting tests read `x` volatile so that forwarding cannot stand in for the lifting they test. 51 goldens change their executions; every other verdict in the suite is unchanged.
- **Lifting keeps the dependency set of the justification it lifts into.** It took the symbols of the remaining predicate and of the value, which put control dependencies into `D`, so a lift of value-assigned writes carried `D = {α}` and the next lift, against an arm with `D = {}`, was refused. That lost `avoidoota/listing20.lit`'s witness once forwarding substituted; master's witness had forwarded `x := 0` into the read it needed to be 17. The dependency relation still takes the predicate's symbols directly, so no dependency is lost.
- **A final value is the co-maximal write, under an order the model admits** (#124). `@x`, and a bare global in a condition, took the last write to `x` in rhb order, `(dp ∪ ppo ∪ rf)⁺`, which leaves the writes of two threads unordered; coherence only asks that some order admit the execution, so the final value was tied to no order it was admitted under. `x := 1 ||| x := 2; r1 := x` allowed `@x = 2 ∧ r1 = 1` under SC, RC11, OCaml and sMRD, though `r1 = 1` puts `x := 1` co-last. Where po leaves two writes to a location the condition asks about unordered, the condition now holds when it holds of the co-maximal writes of some coherence order the assertion's model admits the execution under (`Coherence.admitted_order_where`); a model with no coherence order, Wasm and the session models, admits every po-respecting one. Otherwise the last write is the po-last. Promising semantics and refinement chains are unchanged. `own/atloc-racing-writes.lit` and `own/atloc-racing-sc-stores.lit` are the two shapes of the issue; no other test in the suite changes verdict.
- **A model with no lock order refuses a program with locks** (#125). Only sMRD -- and MRD, which is sMRD on its fragment -- orders critical sections, adding each lock order's `[Unlock];lo;[Lock]` to `hb`; every other coherence model read `lock` and `unlock` as no-ops, so SC let a thread read a write made and overwritten inside another thread's critical section. `MEMORY_MODEL.orders_locks` says which models order them, and `check_model_program` refuses a lock program under any other, naming the lock, as the fragment models refuse what is outside them. Promising semantics orders critical sections too. No test in the suite runs a lock program under a model that now refuses it.
- **A run whose loop runs out of unrollings is no run** (#133). When the step counter ran out inside a loop whose condition still held, sMRD cut the run off there and kept it as an execution with no final registers, so every assertion over them held; under the per-loop counter and under PS1 and PS2 the run instead went on past the loop. A spin-wait message-passing test allowed `b != 7` under every model with a `while` loop, and under PS1 and PS2 with a `do` loop. Unrolling now ends in an exit check, `Ir.Blocked`: a run that would go round again stops there and is dropped -- in sMRD, paths end only at terminal events (`Eventstructures.generate_max_conflictfree_sets`), and under promising semantics a blocked thread never finishes. Loops get as many unrollings as before, under both counters and both semantics, so a run that exits within them is unchanged; a decided exit check makes no branch event, so event numbers stay as they were. Across the litmus suite under every model only `oopsla26_rgsep/MP-repeat.lit` changes, now forbidden under PS1 and PS2 as the paper says.
- **A read of a location nothing writes no longer empties SC and the release-acquire family** (#127). The initial event writes every location, but `Vocab.co` puts it co-before every store whatever its location, so through it `fr = rf⁻¹;co` related a read of `z` to a store to `x`. In `x := 3; r1 := z` that edge closed a cycle with `po`, and SC, VbD, DRFx, DeNovoSync, RA, SRA, CRC and OCaml admitted no execution at all. `Vocab.fr` is now restricted to one location, and RA, SRA and CRC check `co;hb;rf⁻¹` as the equivalent `fr;hb`. Over the whole suite three tests change, each reading a location nothing writes: `own/DOMAIN.lit`, `own/FWD-STRENGTHEN-LIFT.lit` and `rmw/cas_acqrel_failure_reorder.lit` are now allowed under the models that rejected every execution; RA and SRA now agree with WRA on them, and CRC with C11.
- **`true` and `false` are literals** (#129). They lexed as globals, so a condition `allow (true)` reached the solver as an integer-sorted variable and the run aborted with Z3's "invalid argument". They are now keywords for `EBoolean`, in assertions and in program conditions alike; `allow (true)` holds when the model admits any execution. No test used either word as a name.
- **An assertion naming a coherence model and a promising semantics checks each under its own executions** (#128). `allow P [RC11, PS1]`, or the two on separate lines, gave every model the first one's executions and verdict: under `[RC11, PS1]` PS1.0 was said to forbid load buffering, under `[PS1, RC11]` RC11 to allow it. `Context.set_assertions` now resolves `[PS1]` and `[PS2]` to themselves rather than to the model in effect, the promising step no longer rewrites every assertion's model to its own, and `Semantics.step_calculate_executions` adds the other semantics' executions to `model_executions`: a promising run for `[PS1]` and `[PS2]`, sMRD's admitted executions for a coherence model. Data races are UB per assertion model. `--semantics` still chooses one semantics for every assertion.
- **An `sc` read acquires under sMRD, and `sc` accesses synchronise under IMM.** `Forwarding.compute_ppo_sync` computed the `sc` reads and left them out of the events nothing may move before, so under `[smrd]` a data read po-after an `sc` flag load could read stale data; since 0c66850 message passing through an `sc` load was allowed. `acq_rel` reads and writes were left out the same way. IMM matched `W_rel` and `R_acq` in `sw` and `bob` by exact mode, so an `sc` access neither released nor acquired, and MP through `sc` accesses was allowed under `[imm]` with either side `sc`. `own/MP+sc+sc.lit`, `own/MP+rel+sc.lit` and `own/MP+sc+acq.lit` forbid the outcome under sMRD, IMM and RC11. Four goldens gain `ppo` edges out of `sc` reads and keep their verdicts and executions.
- **Redundant-store elimination stays within a thread** (#58). Forwarding a store from an earlier store of the same value drops it, which is sound only when nothing can come between them. Initialising stores are `po`-before every thread through the fork, so a thread's store of a location's initial value was dropped too, and another thread's store to the location, which coherence could put between the two, then went unoverwritten. `popl_bridging/Preserving detour.lit`, the Bridging paper's (POPL 2019) example for IMM's `detour`, was allowed on exactly that execution. It is now forbidden under IMM, as the paper says, and under sMRD and RC11, and is back in the suite. 94 other goldens lose executions, each one an execution with a store dropped this way, and keep their verdicts: `avoidoota/listing15` goes from 1,083 to 429.
- **A write narrowed by a UB assumption writes the narrowed value.** Under `[UB11]`, folding `1 / !r1` to `1` assumes `r1 = 0`, and value assignment already justified `z := r1` as `W z 0` under that assumption. An execution taking that justification still wrote the structure's `r1`, so `symmrd/LB+UB+data+z.lit`'s `allow (r1 != rz)` (#65), the sMRD notes' example of a register appearing to hold two values, had no witness. Executions and freeze results now carry `write_values`: the writes whose value a UB assumption narrowed, with that value. Reads, the execution's value map, deduplication, minimality and the assertion check's final memory all use it. A value that the predicate, forwarding or a program-wide guarantee entails is not recorded, because it is the value the write takes anyway. The test is back in the suite with 125 executions, up from 89; `symmrd/LB+UB+data+z-memory.lit` checks that final memory sees the narrowed value. No other golden changes.
- **A model decides which writes sMRD may elide.** sMRD's write elision dropped a release store that a relaxed store of its own thread overwrites. Under RC11, C11 and IMM that relaxed store continues the release sequence, so an acquire reading it synchronised with nothing, and `rc11` allowed `mp-rs` and `mp-rs-st-eadd-atomics`, which `rc11.cat` forbids. `MEMORY_MODEL.elidable` says which elisions a model lets stand, and the coherence stage rejects an execution built with one it does not: `rc11`, `rc11c`, `rc11z`, `od-lso`, `c11` and `imm` let a release store be elided only by a release store; C++17's release sequence, sMRD and the other models keep every elision. Elaboration still enumerates once for all models. `popl_promising/Page 7 Column 1b.lit` (#61), parked because IMM allowed it, now holds and is back in the suite; `own/sync/writeElisionRel.lit` loses the three executions that elided its release store.
- A directory run (`--all-litmus-tests`) gave every program the same options record, so the model one test's annotation applied stayed in effect for the next test that named none. Each program now gets its own copy.
- **Update atomicity holds when the update's read could be forwarded to.** Forwarding a preceding write into the read of a read-modify-write left that read without an `rf` edge, and `rmw_atomicity`, phrased over `rf`, never saw another thread's write that `co` put between the update's read and write: `x := 0; FADD(x)` could read 0 with `x := 2` in between. Like a volatile access, an update's read and write are no longer elidable by forwarding or write elision. Upd-Stuck (both copies) and `popl_grounding/FADD.lit` now verify; eleven other goldens lose only executions that broke atomicity, Par-Inc going from 11 to the 2 atomic ones.
- `.rf` and `.rmw` can be written in an assertion. The lexer reads `rf` as a register name, which the relation syntax did not accept, so no assertion could name either.
- **Locks are ordered under sMRD.** `lock` and `unlock` produced events that nothing read, so critical sections neither excluded each other nor ordered anything. A lock now acquires and an unlock releases in `ppo`, so nothing leaves a critical section, and `Coherence.SMRD` requires some lock order: a total order of the critical sections on each lock, respecting `po`, whose unlock-to-next-lock edges join `hb`. Locks are reentrant, so only an outermost lock/unlock pair is a section, as with Java's monitors; a section that never unlocks must be last. `on_thin_air_reads19/P5.lit` (#54) and `sevcik_thesis/Skip/LB+locks.lit` (#64), parked because sMRD allowed what mutual exclusion forbids, now hold and are back in the suite. `sevcik_thesis/Skip/Redundant Write after Read Elimination.lit` asserted `allow (r1 = 1 && r2 = 2)`, the JMM's verdict on the *transformed* program, over a copy with one anonymous lock, and passed only because locks did nothing. It is now Ševčík's source program (§5.3.1), with locks `m1` and `m2`, asserting the thesis' `forbid`; `Redundant Write after Read Elimination (transformed).lit` is the program with `x := r1` removed, which the JMM allows and sMRD, being coherent, forbids. Five other goldens that use locks gain `ppo` edges and keep their verdicts; the other models still ignore locks.

### Changed
- Litmus tests annotated with the name of their source -- `[Sevcik]`, `[Problem]`, `[JR]`, `[Bridging]`, `[Grounding]`, `[Bubbly]`, `[Soham]` -- now name the coherence model they were checked under, `[sMRD]` or `[IMM]`, and cite the publication their expected verdict comes from in a comment on their first line. Verdicts are unchanged on all 55 files. `[Power]` is unchanged.
- CI runs the litmus tests and the episodicity tests as workflows of their own, `litmus-tests.yml` and `episodicity-tests.yml`, so the README shows a badge for each. They share their setup through a reusable workflow, `integration-suite.yml`. The remaining integration tests run in `ci.yml`, after the unit tests, and `integration.yml` is gone.
- **A `volatile` access is never lifted out of a branch.** Lifting merges two conflicting writes from the arms of a branch into one the branch no longer guards, pairing the arms' reads by relabelling as it goes, which hoists the reads too. It is now refused when either write is volatile, or when the relabelling pairs a volatile read with a different read of the other arm; a read before the branch, shared by both arms, is not lifted and stays pairable. Non-elision and non-lifting are what `volatile` means: it still derives no ordering. `own/volatile-write-not-lifted.lit` and `own/volatile-read-not-lifted.lit` test it, against relaxed controls; no other test changes.
- An allocation may reuse the address of an earlier allocation when a free may release the earlier one first. Allocations used to be distinct in every case, in the structure's constraints and in the static dependency constraints alike. `Eventstructures.may_reuse` now decides per pair whether an intervening free may release the earlier allocation; for such pairs the execution-level check decides. Seven tests in `litmus-tests/own/` cover reuse after a free, through a loaded pointer, and across threads, and the cases that stay distinct.

## [0.2.0] — 2026-09-27

Second pre-release, accompanying the artifact for "Episodic Loops: Finitary Event
Structures and Operational Semantics for C11 Programs with Retries".

### Breaking
- The source names `Sevcik`, `Problem`, `JR`, `Bridging`, `Grounding`, `Bubbly` and `Soham` are no longer model names: a model name is valid when the Relaxed Memory Model Zoo has it. A test using one is now an unknown-model error unless `--allow-unknown-model` is given. Name the model the test is checked under, `[sMRD]` or `[IMM]`.

- **Unknown memory model names are an error.** An annotation naming a model MoRDor does not implement, such as `[C11]`, `[RA]`, `[Promising]` or `[JMM]`, used to log a warning and fall back to the default model. It now fails, and `--allow-unknown-model` brings back the old warn-and-continue behaviour ([#86](https://github.com/christiankissig/mordor/issues/86)).
- **A test that names no model runs under sMRD.** The default used to be `undefined`, which checks RMW atomicity and nothing else, so a test with no annotation got no coherence or thin-air checking at all (`9fd5a15`).
- **`@x` in an assertion means the final value stored at `x`.** It used to be the location variable, which made every `@` assertion vacuous. It also sees writes that reach `x` through a pointer ([#84](https://github.com/christiankissig/mordor/issues/84), [#5](https://github.com/christiankissig/mordor/issues/5)).
- **A program's expressions are over registers.** A global, `@x` or `&` in an expression, and `free` of a global, are parse errors naming the statement's line and column. A global is read by a load and written by a store, each its own event, and its address is taken only by `r := &x`. Before, a global in an expression silently meant its address rather than its value: `r := x + 1` added one to where `x` lives, `if (x = 1)` compared that address, `*p := v` wrote to `p` itself, and `A := &x` stopped the run with "Unsupported unary operator &". `cas` and `fadd` on a global now take a reference, `rx := &x; r := cas(…, rx, …)`, and the 24 corpus programs that passed a global directly are rewritten that way.
- **Statements after a parallel block run.** They used to be silently dropped. They now execute once every thread in the block has finished ([#81](https://github.com/christiankissig/mordor/issues/81)).
- **Library API:** `USet.inplace_union` takes the set it mutates as `~into` ([#88](https://github.com/christiankissig/mordor/issues/88)). `symbolic_execution` has two new fields, `co` and `justifications`. `Eventstructures.dslwb` takes an optional `?state`.
- **The Java Causality Test Cases have left the scanned suite.** They are now annotated `[JMM]` and live in `litmus-tests-jmm/`.
- Removed the `promising` memory model, which was a misleading alias to IMM: promising semantics is operational and cannot be expressed by the axiomatic coherence checker. The promising-paper litmus tests are kept for reference under `litmus-tests-promising/`, with runnable `[IMM]` copies in `litmus-tests/popl_promising/` ([#9](https://github.com/christiankissig/mordor/pull/9)).

### Added

#### Memory models
- 24 models from the [Relaxed Memory Model Zoo](https://rmm-zoo.kissig.org), each defined over relations the pipeline already computes, and each selectable by the zoo's name:
  - `[SC]`, `[VbD]`, `[TSO]`, `[x86-TSO]` and `[ClightTSO]`. Fences and atomic instructions, a CAS or FADD, flush TSO's store buffer, as in herd's `tso.cat`.
  - `[RC17]`, RC11 with C++17's release sequences; `[RC11z]`, RC11 with allocations and frees ordered as writes; `[OD-LSO]`, Ou and Demsky's `acyclic(sb ∪ rf)` over the C/C++11 model.
  - `[MRD]`, as sMRD on programs that access only named globals and allocate nothing. Any other program is refused, because there sMRD admits executions MRD does not.
  - `[RA]`, `[SRA]` and `[WRA]`, Lahav and Boker's release-acquire family, and `[CC]`, weak causal consistency.
  - `[Coherence]`, `[PC]`, `[PRAM]`, `[Causal]`, `[Slow]` and `[Local]` from Steinke and Nutt's lattice, decided by searching for a view per thread.
  - `[POCausal]`, and the session guarantees `[RYW]`, `[MR]`, `[MW]` and `[WFR]`.

  SC, TSO, Coherence, RA, SRA, WRA, RC17 and OD-LSO agree with herd7 on the zoo's cat models across 1,838 outcome checks over 21 programs, with one known exception. Outside the release-acquire fragment, herd's RA cat files let a thread read its own later write, and MoRDor never generates that execution. The zoo's ordering edges hold execution by execution across the whole suite. `litmus-tests/rmm-zoo/models/` has one file per separating shape, asserting the verdict of every model there is evidence for: herd7, an equivalence or ordering edge of the zoo, or the model's definition, each named in the file's header. Every model is a check on the executions MoRDor generates, which are free of thin air, so a model weaker than sMRD cannot show a behaviour only thin air gives.

#### Command line
- `--output-mode isa` labels each loop-body event with its actual iteration. The step-counter unroller now tags every copy it makes of a loop body with the copy's iteration (`loop_ctx.iters`, parallel to `loops`), the interpreter records it per event (`loop_iters`), and the export zips it with the loop ids; before, the "iteration" was the loop id again (`t1.5@4:4#0`), so the two iterations of a body were indistinguishable. Copies of one instruction interpreted on several branch paths — the statements after an unrolled loop, once per exit path — now share one label (`#k` is the position within the instruction's declared events), and each future carries the reads-from of its witness execution under `rf`, as data about that execution, not as part of the future.
- `executions` command, and `POST /api/executions`, for exporting executions with their events and relations (`6db5120`).
- `justifications` command, which lists the program's justification set and the elaboration step behind each justification, as text or with `--output-mode json` ([#80](https://github.com/christiankissig/mordor/issues/80)).
- `dependencies` command. It used to print a TODO and exit 0 (`3d3a934`).
- `--output-mode isa`, an Isabelle interchange export ([#10](https://github.com/christiankissig/mordor/pull/10)).
- `--allow-unknown-model` ([#86](https://github.com/christiankissig/mordor/issues/86)).
- sMRD has a symbolic form: its axioms as constraints over a whole justification combination, in two levels — `hb` as `(dp ∪ ppo)⁺`, then with the release/acquire edges `[W_rel];rf;[R_acq]` that the read-from decides — registered beside the model and asked for by name ([#102](https://github.com/christiankissig/mordor/issues/102)). It decides every one of rcu-2's 2,916 combinations at step counter 2, where the first level alone left 46 undecided, and computes all **1,966** of its futures in 19 minutes on 16 threads. Every other model keeps the enumeration path.
- `futures` computes the futures from one witness execution per future instead of from every execution ([#99](https://github.com/christiankissig/mordor/issues/99)). Every execution of a justification combination has the same future, so a combination needs one execution the model admits, or the knowledge it has none; for sMRD a solver query per combination decides that, for other models a search. The futures are the same on all 375 corpus programs and the 30 tracked programs that finish either way; rcu-2's are computed for the first time: 224 at step counter 1 in 30 s, and 1,964 at step counter 2 in 30 minutes on 16 threads, with 46 combinations left undecided and reported. `--all-executions` restores the old behaviour.

- A test can have several assertions, one per line, and an assertion can name several models: `forbid (c) [RA, SRA, SC]`. ### Fixed

#### Assertion checking
- `forbid` assertions reported valid without looking at a single execution (`4998e70`).
- Conditions were checked without the execution's own path predicates, so outcomes the execution contradicts still came back satisfiable (`48026cd`).
- Set-membership tests gave answers about events the execution does not contain (`0bca217`).
- Refinement verdicts depended only on the `allow`/`forbid` keyword; neither program was ever run ([#85](https://github.com/christiankissig/mordor/issues/85)).
- Use-after-free and unbounded-dereference detection only found a pointer that was the allocation's own symbol, such as a register assigned by `malloc`. A pointer loaded from memory is a read's symbol, and its rf edge to the allocation was never followed, so a use after free through a pointer held in a global, or in any other cell, went unreported. `symmrd/LB+UB+data+arr.lit` now reports an unbounded dereference: in executions where `r1 = 1`, its read `*(ra + 1)` is past the end of the allocation and takes its value from `x` or `y`, not from any store to the allocation. Those executions exist only because an offset into an allocation may still alias a global.
- A condition over registers holding references compared the values of the globals they refer to: over `rp := &x; rq := &y`, `forbid (rp = rq)` failed whenever `x` and `y` held the same value.

#### Interpretation
- Every event of every thread had thread index 0. The parser annotates a thread body before the enclosing block advances its thread id, so each body saw 0. The interpreter now numbers threads as it enters them, nested blocks included, and the code after a join is back in its parent's thread. Canonical execution renderings, and so the goldens, name the real threads.
- Symbolic `while` and `do` loops produced no executions ([#11](https://github.com/christiankissig/mordor/pull/11)).
- `do { B } while (c)` never reached the loop after its first iteration (`76cc05c`).
- `x := malloc n` did not store the address to `x`, so a later load from `x` read whatever it held before, and two allocations held in globals could be the same cell. It is now an allocation followed by a store to `x`.
- `free(x)` of a global freed nothing: the parser turned it into a free of an unbound register, so the deallocation had no location. It is now refused (see Breaking).
- A global reached only through a reference, `r := &y`, was left out of the constraint that distinct globals are distinct locations. Forwarding and elaboration read that constraint, so a write through the reference was treated as possibly overwriting every other global.
- `interpret` printed every deallocation as `Free _`.
- The `e / !r -> e` undefined-behaviour fold was applied under every model. It now applies only when the model allows it, as `[UB11]` does (`365fa76`).

#### Dependencies and elaboration
- Value assignment took a value from whichever model the solver returned. It now fills in a value only when the justification's predicates force it. This closes an out-of-thin-air witness in `avoidoota/listing16.lit` ([#43](https://github.com/christiankissig/mordor/issues/43), `ae177d0`).
- Value assignment dropped the guard that fixed a write's value, and fired even when it left the write unchanged (`71ba377`, `bf93af4`).
- Forwarding is followed when freezing the dependency relation, so a forwarded read no longer drops a dependency (`f7c45d3`).
- An elided write could stop a read from reading an earlier write (`15df03a`). `dslwb` now decides shadowing under the same path predicates as the rf edge beside it (`540171f`).
- Preserved program order kept same-location read pairs, and now orders accesses that *may* alias ([#38](https://github.com/christiankissig/mordor/issues/38)).
- The RMW part of preserved program order composed `ppo_sync` with each (read, write) pair rather than (write, read), as the episodic loops paper defines it. For a CAS or fetch-and-add that ordered nothing, so neither acted as a synchronisation point, and forwarding could cross one. `popl_bridging/ARM FADD.lit` drops from 93 to 79 executions. No verdict changes.

#### Coherence
- sMRD's happens-before relation had no synchronises-with edge, so release-acquire chains were invisible to it ([#67](https://github.com/christiankissig/mordor/issues/67), [#68](https://github.com/christiankissig/mordor/issues/68)).
- IMM's coherence check overwrote a set it shared across every candidate coherence order, so the search's answer depended on the order candidates were tried ([#88](https://github.com/christiankissig/mordor/issues/88)).
- A nonatomic store or load matched RC11's "relaxed or stronger" tests, because matching also asked the mode fields an event's type does not use, and those default to relaxed. A nonatomic store could then synchronise two fences (`own/nonatomic-store-no-sync.lit`).
- RC11's SC check ignored sc stores and loads: it collected sc accesses from `Init` events, of which there are none, so only `fence(sc)` took part. Store buffering over sc accesses came out allowed (`own/SB+sc.lit`). Its `scb` also had `sbl;hb` where RC11 has `sbl;hb;sbl`.
- The coherence order grouped writes by location without the execution's predicates, so a write through a pointer was never ordered against a write to the location it points at, and a read could take the value it had overwritten. This applied under every model (`own/ptr-overwrite-coherence.lit`). `fowm2024/load intro` (both variants) drop from 4 to 1 execution, `own/JCTC12.lit` from 12 to 8 and `avoidoota/listing9.lit` from 21 to 19. No verdict changes.
- RC11 applied the full coherence check only to executions without RMWs (`27271c9`), and built both ends of `psc_base` from one shared set (`cbb4b3a`).
- IMM and RC11 were over-permissive ([#9](https://github.com/christiankissig/mordor/pull/9)): release/acquire synchronisation ignored the mode lattice, the coherence axioms were skipped for programs with fewer than two writes, and the init write could be permuted out of first place.

#### Episodicity
- Many fixes to the write and events conditions and to loop handling: loop conditions and guards recorded per path and per occurrence, allocation interiors kept apart from other allocations, reads no longer reported against writes they conflict with, and RMW preserved program order used in the events condition. `hp-1` and `rcu-1` are back in the suite and reported episodic.

#### Web UI

- Errors from the server never reached the log: the page looked for a field the server does not send, so a parse error or an unknown model only turned the status to *Error*. They are now logged. A parse error quotes the offending line with a caret, and the editor marks the token. Its message gives the 1-based column where the token starts and names the token, where it used to give a column past the token's end and say only "Parse error: Parse error at …". The program is sent untrimmed, so line numbers are the editor's.
- The justification panels are laid out one entry per line, and their Show/Hide button works (`0779cdf`).
- Every event in a graph was drawn with the ring meant for the initial event, and in the light theme edge labels sat on a dark backing.
- Messages about loading a file, loading a program from a link and sharing were put at the top of the log, above older entries.
- The language reference's examples: the CAS example did not parse and read a failed swap as success, the store-buffering example was not store buffering, the load-buffering example allowed an outcome only thin air produces, and all of them used `[x = 0]`, a de facto guarantee, as if it initialised memory. `cas` and `fadd` now say what they put in the register, and the model names `c11` and `sc`, which MoRDor rejects, are gone.
